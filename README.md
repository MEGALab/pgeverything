# PGEverything

**One PostgreSQL 16 image with everything a developer needs to build a modern AI Foundry.**

Instead of running nine databases and services — Postgres, MongoDB, Neo4j, InfluxDB, Redis,
Pinecone, Elasticsearch, Auth0, plus a cache — PGEverything gives you one PostgreSQL server,
one port, nine workloads. Everything is a Postgres extension, so it is all transactional,
backed up together, and queried in one SQL dialect.

| Capability | Powered by |
|---|---|
| **SQL** | Core PostgreSQL 16 |
| **NoSQL / document** | Native JSONB + GIN |
| **Graph** | Apache AGE (openCypher) |
| **Time-series** | TimescaleDB |
| **Pub/Sub** | pgmq (durable queues) + `LISTEN`/`NOTIFY` |
| **Vector** | pgvector + pgvectorscale |
| **Key-value cache** | pgcache (jsonb values, TTL) |
| **Full-text search** | core tsvector + GIN |
| **Auth / RLS** | pgauth (JWT via pgjwt) + Row-Level Security |

Plus `pg_cron`, `pg_trgm`, `pgcrypto`, `pgjwt`, `pg_stat_statements`, and optional **PostGIS**.

## Quick start

```bash
make build      # build the image (compiles AGE + pgmq)
make up         # start it, wait for healthy
make smoke      # verify all nine capabilities
make shell      # psql in
```

Connect: `postgres://postgres:postgres@localhost:5432/pgeverything`

### Provisioning databases

Two commands cover two needs — the container must be running (`make up` first):

**Grant an existing user on a database + schema.** Creates the database and/or schema if they
don't exist, then grants an **already-existing** login role access to them. It never creates the
role or changes a password: `DB_USER` must exist and `DB_PASSWORD` must be its current password
(verified by a login attempt — a wrong password aborts before anything is created):

```bash
make database-create DB_NAME=analytics SCHEMA_NAME=reporting DB_USER=analyst DB_PASSWORD=<existing-pw>
```

The role is granted `CONNECT` on the database plus `USAGE`/`CREATE` and full CRUD on the schema
(including default privileges for future tables). A **newly-created** database has its default
`PUBLIC` `CONNECT` revoked, so only granted roles can connect; an existing database is left as-is.

**Create a new database with a fresh admin user.** Generates a role (UUID name + 12-word
passphrase) that owns a brand-new database:

```bash
make tenant-create        # prompts for the new database name
```

> Isolation relies on `CONNECT` privileges, which superusers bypass by design — so the
> `postgres` superuser still administers every database, and `app_user` keeps its access to the
> primary DB.

### Replication

Stand up a streaming read-replica on another server:

```bash
make replication-enable   # on the PRIMARY host: authorize a replica (prompts)
make replicant            # on the REPLICA host: clone repo, then run this (prompts)
make replicant-smoke      # verify replication end-to-end (separate from `make smoke`)
```

Full walkthrough and caveats: [Physical replication (cross-host)](#physical-replication-cross-host).

### Secrets

Store encrypted secrets (API keys, credentials) in a `vault` schema:

```bash
make secrets-init         # bootstrap the vault + an admin in a database (prompts)
make secret-user-create   # admin creates a read/write user (autogenerated creds)
make secrets-create       # that user encrypts + stores a secret
make secrets-smoke        # verify the vault end-to-end (separate from `make smoke`)
```

Full walkthrough: [Secrets management (vault)](#secrets-management-vault).

## Examples

**Document (JSONB)**
```sql
CREATE TABLE docs (id bigserial, doc jsonb);
CREATE INDEX ON docs USING gin (doc jsonb_path_ops);
SELECT * FROM docs WHERE doc @> '{"status":"active"}';
```

**Graph (AGE)**
```sql
LOAD 'age'; SET search_path = ag_catalog, "$user", public;
SELECT * FROM cypher('g', $$ MATCH (a)-[:KNOWS]->(b) RETURN a,b $$) AS (a agtype, b agtype);
```

**Time-series (TimescaleDB)**
```sql
SELECT create_hypertable('metrics', 'ts');
SELECT time_bucket('5 minutes', ts) AS bucket, avg(value) FROM metrics GROUP BY bucket;
```

**Pub/Sub (pgmq)**
```sql
SELECT pgmq.create('jobs');
SELECT pgmq.send('jobs', '{"task":"embed"}');
SELECT * FROM pgmq.read('jobs', vt => 30, qty => 1);   -- read with 30s visibility timeout
```

**Vector (pgvector)**
```sql
CREATE TABLE items (id bigserial, embedding vector(1536));
CREATE INDEX ON items USING hnsw (embedding vector_l2_ops);
SELECT id FROM items ORDER BY embedding <-> '[...]' LIMIT 5;
```

**Key-value cache (pgcache)**
```sql
SELECT cache_set('user:1', '{"name":"alice"}'::jsonb, ttl => 60);  -- ttl seconds, NULL = forever
SELECT cache_get('user:1');    -- {"name": "alice"}, or NULL once expired
SELECT cache_incr('hits');     -- atomic counter, returns new value
SELECT cache_del('user:1');    -- true if the key existed
```

**Full-text search (core tsvector)** — no extension needed
```sql
CREATE TABLE articles (
  id   bigserial,
  body text,
  fts  tsvector GENERATED ALWAYS AS (to_tsvector('english', body)) STORED
);
CREATE INDEX ON articles USING gin (fts);
SELECT id FROM articles WHERE fts @@ to_tsquery('english', 'quick & fox');
```

## Authentication & Row-Level Security

`pgauth` gives you bcrypt password hashing (pgcrypto), JWT sessions (pgjwt), and per-user row
isolation via PostgreSQL Row-Level Security — no external auth service required.

> ⚠️ **Two things that make or break RLS:**
> 1. **Connect as a non-superuser role.** Superusers *bypass* RLS. PGEverything ships an
>    `app_user` role for exactly this — your app connects as it (set `PGE_APP_USER_PASSWORD`),
>    or you `SET ROLE app_user`. As `postgres` you will see every row.
> 2. **Set `PGE_JWT_SECRET`.** The default is insecure and public. Anyone with the secret can
>    forge sessions. The secret is stored in a protected table only `SECURITY DEFINER`
>    functions can read — `app_user` cannot read it.

**The users table** (created for you by the `pgauth` extension):
```sql
-- auth.users(id uuid pk, email text unique, pass_hash text, role text, created_at timestamptz)
SELECT auth.register('alice@example.com', 's3cret');   -- bcrypt-hashes the password, returns the new uuid
```

**Log in → validate the session on the server:**
```sql
SELECT auth.login('alice@example.com', 's3cret');      -- returns a signed JWT (1h expiry), or NULL if wrong
SELECT auth.authenticate('<that jwt>');                -- verifies signature + expiry, loads claims into the session
SELECT auth.uid();                                     -- alice's uuid, or NULL if unauthenticated
```

**Per-user data with RLS** — every row belongs to its creator, and users only ever see their own:
```sql
CREATE TABLE notes (
  id       bigserial PRIMARY KEY,
  owner_id uuid NOT NULL DEFAULT auth.uid(),            -- auto-stamped with the logged-in user
  body     text NOT NULL
);
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;
CREATE POLICY notes_owner ON notes
  USING (owner_id = auth.uid())                         -- read: only my rows
  WITH CHECK (owner_id = auth.uid());                   -- write: can't create rows for others
GRANT SELECT, INSERT, UPDATE, DELETE ON notes TO app_user;
```

**Putting it together** (as the application role):
```sql
SELECT auth.authenticate(auth.login('alice@example.com', 's3cret'));
SET ROLE app_user;                                      -- RLS now applies
INSERT INTO notes (body) VALUES ('only alice can see this');
SELECT * FROM notes;                                    -- returns only alice's rows
```

`notes` is a working example baked into the image; `auth.role()` exposes the JWT `role` claim
for role-based policies. (Open registration and 1-hour non-refreshable tokens are dev defaults
— restrict `auth.register` and add refresh tokens for production.)

## Configuration

| Env var | Default | Purpose |
|---|---|---|
| `POSTGRES_PASSWORD` | `postgres` | superuser password |
| `POSTGRES_DB` | `pgeverything` | initial database |
| `PGE_PORT` | `5432` | host port |
| `PGE_ENABLE_POSTGIS` | `false` | enable PostGIS at first boot |
| `PGE_SHARED_BUFFERS` | `256MB` | shared_buffers — set to ≈25% of RAM |
| `PGE_WORK_MEM` | `16MB` | work_mem per sort/hash operation |
| `PGE_MAX_CONNECTIONS` | `100` | max concurrent connections |
| `PGE_JWT_SECRET` | *(insecure default)* | pgauth JWT signing secret — **change this** |
| `PGE_APP_USER_PASSWORD` | *(empty)* | set to enable direct `app_user` logins (else NOLOGIN) |

> ⚠️ **If you change `POSTGRES_DB`**, you must also update `cron.database_name` in
> `docker-compose.yml` (and `rootfs/postgresql.conf.d/pgeverything.conf`) to the same value.
> pg_cron requires them to match — otherwise first-boot init fails with
> *"CREATE EXTENSION pg_cron must be run in the database named by cron.database_name"*.

## Secrets management (vault)

Use Postgres as a secrets manager: a per-database **`vault`** schema stores credentials/API
keys encrypted with **pgsodium** authenticated encryption. The encryption key is derived from a
root key kept **outside** the database (env `PGE_VAULT_KEY`, loaded by pgsodium at startup), so
a `pg_dump` only ever contains ciphertext + key IDs. Access is governed by app-level RBAC.

Enable it in any database and bootstrap an admin:
```bash
make secrets-init                 # prompts for the target database; autogenerates the admin's UUID + passphrase
```

| Command | Who | What |
|---|---|---|
| `make secrets-init` | operator | prompts for the DB; creates the `vault` schema + a pgsodium key + a master admin (autogenerated UUID + 12-word passphrase, shown once) |
| `make secret-user-create` | admin | create a `read`/`write`/`both` user — autogenerates username + password |
| `make secret-user-deactivate` | admin | deactivate a secrets user |
| `make secret-user-passwd` | user | change your own password (prompts current + new) |
| `make secrets-create` | write/both user | encrypt + store a secret → returns its UUID |
| `make secret-read` | read/both user | decrypt + reveal a secret's plaintext by UUID |
| `make secrets-update` | write/both user | replace a secret's value by UUID |
| `make secret-delete` | write/both user | delete a secret by UUID |
| `make secret-red-alert` | admin | **lock the whole vault** — all secret access is refused |
| `make secret-stand-down` | admin | reactivate the vault |
| `make secrets-smoke` | operator | verify the vault end-to-end (ephemeral DB) — separate from `make smoke` |

**RBAC model:** the **admin** manages users but *cannot* read or write secrets (no permission);
**read/write/both** users manage secrets but cannot manage users. Every operation authenticates
with a vault username + password (independent of Postgres roles).

> ⚠️ **Notes:** set `PGE_VAULT_KEY` (`openssl rand -hex 32`) in production — the default is
> insecure. The root key lives in the container environment, not the DB. A Postgres **superuser
> can still read the `vault.secrets` table**, but only sees ciphertext; decryption requires the
> pgsodium key. Autogenerated user passwords are shown **once** at creation.

## Schema users

CRUD for **real Postgres login roles scoped to a schema**, in any database. Each user's name is
a UUID and its password is a 12-word EFF-diceware passphrase; it's granted read/write on one
schema and tracked in a per-database `pgusers.schema_users` registry. Every command prompts for
the target database.

```bash
make user-create            # prompts db + schema → prints a UUID + 12-word passphrase (once)
make user-read              # prompts db + user id → registry record + login status
make user-update-password   # prompts db + user id + new password
make user-deactivate        # locks the user out (random undisclosed passphrase); keeps data
make user-delete            # DROP OWNED BY + DROP ROLE — wipes the user + all its objects
```

> ⚠️ **Notes:** the passphrase is shown only at creation. `user-deactivate` resets the password
> to an undisclosed passphrase (account + data preserved). `user-delete` uses `DROP OWNED BY`,
> which removes the user's objects across **all schemas of the chosen database**; a role that
> also owns objects in *other* databases must be deleted there too before the role fully drops.

## Databases

Two ways to provision, for different needs:

- **`make database-create DB_NAME=… SCHEMA_NAME=… DB_USER=… DB_PASSWORD=…`** — grant an
  **existing** user access to a database + schema, creating the database/schema if missing (see
  [Provisioning databases](#provisioning-databases)). Never creates the user.
- **`make tenant-create`** — prompts for a new database name, creates it, then bootstraps a
  per-DB **admin** user (autogenerated UUID + 12-word passphrase) that **owns** the database
  (via the `user-create` flow). The admin is scoped to that database — not a cluster superuser.

## Physical replication (cross-host)

Run a second PGEverything container as an **asynchronous streaming read-replica** of a primary
running on another server. Two steps, two hosts:

**1. On the primary host** — authorize replication (idempotent, no restart):
```bash
make replication-enable      # prompts for the replica's CIDR + a replication password
```
This creates a `replicator` role, opens a `pg_hba` rule for the replica's network, and sets a
`wal_keep_size` buffer. Make sure the primary's Postgres port (`5432`) is reachable from the
replica (firewall).

**2. On the replica host** — clone this repo, then:
```bash
make replicant               # prompts for primary host/port/user/password + replica port
```
It writes the answers to `.env`, builds the image, and starts `pgeverything-replica`, which
`pg_basebackup`s from the primary on first boot and comes up as a hot standby.

**Verify** (separate from the single-node `make smoke`):
```bash
make replicant-smoke         # standby? streaming? read-only? data propagates?
make replica-status          # quick recovery + wal-receiver view
```

> ⚠️ **Notes:** replication is asynchronous (a small window of un-replicated commits can be
> lost on failover). The replica is **read-only** — writes error out, and `pg_cron` is dormant
> on it. Traffic is unencrypted unless you add `sslmode=require` (do this in production). v1
> uses `wal_keep_size` rather than a slot, so a replica that's down longer than the buffer may
> need a re-seed (`docker compose -f docker-compose.replica.yml down -v` then `make replicant`).
> To dry-run on a single host, point `PGE_PRIMARY_HOST` at your host's published `5432` and set
> a different `PGE_REPLICA_PORT`.

## Expert agent (Claude Code)

PGEverything ships a **Claude Code subagent** — *PGEverything Expert* — a principal-level
Postgres DBA, data architect, and data engineer that designs and builds the right data storage
for whatever you're working on, entirely on PGEverything. It knows every capability (relational,
JSONB, graph, time-series, pub/sub, vectors, cache, full-text, auth/RLS, secrets) and all the
`make` commands, and it defaults to secure, well-indexed, operable designs.

The agent definition lives at
[.claude/agents/pgeverything-expert.md](.claude/agents/pgeverything-expert.md).

**Install it:**
- **This project** — it's already active (any Claude Code session in this repo can use it).
- **Another project** — copy the file into that repo's `.claude/agents/`.
- **Everywhere (your machine)** — copy it to `~/.claude/agents/`:
  ```bash
  mkdir -p ~/.claude/agents && curl -fsSL \
    https://raw.githubusercontent.com/<your-org>/pgeverything/main/.claude/agents/pgeverything-expert.md \
    -o ~/.claude/agents/pgeverything-expert.md
  ```
  (or just `cp .claude/agents/pgeverything-expert.md ~/.claude/agents/`).

**Use it:** Claude Code delegates to it automatically for data-storage/design work, or invoke it
explicitly — e.g. *"use the pgeverything-expert to design storage for a multi-tenant chat app
with message search and per-user embeddings."*

## Design

Built on `timescale/timescaledb-ha:pg16` (which bundles TimescaleDB + pgvector +
pgvectorscale); Apache AGE and pgmq are compiled from source in a builder stage, and
`pgcache` and `pgauth` are first-party pure-SQL extensions staged into the image, and
`pgjwt` (JWT sign/verify) is installed from source in the builder stage. PostgreSQL 16 is the
highest major where all the third-party extensions have working builds today — Apache AGE
is the version limiter.

Full design spec: [docs/specs/v0.1.0.md](docs/specs/v0.1.0.md).
